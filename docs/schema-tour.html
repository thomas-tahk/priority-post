What migration 0007 did to the schema

One new table, no change to any existing one — and why the shape of it is different from the tables around it.

The whole schema

Seven tables, every column. Three of them reference each other; the other four stand alone. Only one table is new — assistant_turns, in pink, in the second figure.

The other three point at nothing and nothing points at them. That is the whole reason they sit apart:

entity — a thing that exists and changes log — a record that something happened added by 0007

The change itself

The entire migration. Read what is not here: no ALTER TABLE, no new column on an existing table, no backfill, no index rebuild.

CREATE TABLE "assistant_turns" (
  "id"      serial PRIMARY KEY NOT NULL,
  "role"    text NOT NULL,
  "content" text NOT NULL,
  "at"      timestamp with time zone DEFAULT now() NOT NULL
);
Why that matters. A migration that only adds a table is the safest kind there is. The old code doesn't know the table exists, so it keeps working; the new code finds it empty, which is a valid starting state. Nothing to roll back but a DROP TABLE. Compare that to adding a NOT NULL column to tasks — every existing row needs a value, and until the new code deploys the old code is writing rows without one.

Two shapes of table

The thing worth taking from this schema isn't the new table — it's that the seven tables are really two different kinds of thing, and you handle them differently.

entity goals · tasks

A row is something. It exists, you edit it, you eventually finish or delete it.

  • Rows get UPDATEd. Rename a task, change its urgency, set done_at.
  • They point at each other. tasks.goal_id is a foreign key — the database itself refuses a task pointing at a goal that doesn't exist.
  • Deleting one is a real question — what happens to the rows pointing at it?

log sent_reminders · sent_digests · activity · assistant_turns

A row is a thing that happened. It was true at a moment and stays true forever.

  • Append only. Nothing in the app UPDATEs these. You add rows and read them back.
  • Mostly no relationships. Three of the four point at nothing.
  • Deleting is a retention question, not a correctness one — "how far back do we keep?", not "what breaks?".

Once you see that split, the column choices stop looking arbitrary. Every log table ends in a timestamp, because when is the whole point of the row. No log table has an updated_at, because nothing updates.

The two foreign keys, and why they behave differently

A foreign key is a promise the database enforces: this number points at a real row in that other table. It also forces you to answer one question up front — what happens to me when the row I point at is deleted? The schema answers it differently in the two places it comes up, and the difference is the interesting part.

RelationshipOn deleteWhat that means in the app
tasks.goal_id → goals.id SET NULL Delete the goal “Get hired”, and every task under it survives — they just stop belonging to anything. Correct, because “update my résumé” is still a real task you still have to do. A goal is a label on a task, not its reason for existing.
sent_reminders.task_id → tasks.id CASCADE Delete the task, and its “I already pinged you about this” rows are deleted with it. Correct, because a reminder about a task that no longer exists is meaningless — and if the row lingered and the id were ever reused, it would suppress a ping for a different task entirely.
The third option you'll see elsewhere is RESTRICT — refuse the delete while anything still points at the row. It's the right answer when the pointing rows are valuable and you'd rather fail loudly than quietly destroy them. It's wrong here: you'd be unable to delete a goal until you'd hand-cleared every task under it.

Why the new table points at nothing

“It stores a conversation about my tasks — shouldn't it link to the tasks?”

It shouldn't, and the reason is a useful test to remember: a foreign key is for a reference the database can check. A turn in the conversation looks like this:

role:    "user"
content: "actually move that one to saturday instead"

There is no task id in there. There is no task id anywhere in a turn — the reference lives in English, and it is resolved by the model reading the previous turns, not by Postgres. A task_id column here would be null on nearly every row, wrong on some, and enforce nothing.

The rule of thumb: add a foreign key when the child row is about exactly one parent row and becomes nonsense without it. sent_reminders passes that test — a ping is about one task, period. assistant_turns fails it — a turn is about the conversation, and it stays perfectly readable after every task it mentions is gone.

Column choices worth knowing

timestamp with time zone — every time column in this schema

Despite the name, it does not store a zone. It stores an absolute instant (UTC internally) and renders into whatever zone you ask for. Plain timestamp stores wall-clock digits with no idea what they mean — “2pm” with no answer to “2pm where?”.

This is not academic here. Vercel's functions run in UTC and that cannot be changed; your laptop is Denver. With plain timestamp, the same task would read 2pm locally and 8pm in production. It's the same class of bug that put a test task six hours late last week — the storage type was already right, the model was doing the conversion twice.

serial vs. a natural primary key

Six tables use serial — an auto-incrementing integer with no meaning. One doesn't:

sent_digests.day  text PRIMARY KEY   -- '2026-09-23'

That's deliberate. The primary key is the fact being recorded: one digest per calendar day. The database now enforces "at most one row per day" for free — a second insert for the same day is rejected rather than producing a duplicate evening digest. A serial id would have allowed two rows for Tuesday, and the no-double-send rule would have had to live in application code instead, where it can be forgotten.

text for role, not an enum

role only ever holds 'user' or 'assistant', which looks like a textbook case for a Postgres ENUM. It's text because of a rule in this repo's CLAUDE.md: standard SQL only, no Postgres-only features until phase 3, so the database stays swappable. The cost of that choice is real — the database won't stop a typo'd 'assitant' — and it's paid knowingly.

Why the table exists at all

The old gateway bot was a process that never stopped, so it could hold the conversation in a variable in memory. The new endpoint is a function: it wakes up, answers, and is gone. Nothing carries over — which is fine for "what's next?" and fatal for "move that one to Saturday instead".

So the conversation had to land somewhere durable, and Postgres was already there. Two decisions inside that:

  • Plain text, not the raw API transcript. The model's real message list contains tool-call plumbing — a tool_use block must always be followed by its matching tool_result, or the next request is rejected outright. Store that raw and a window that cuts between the pair produces a conversation the API refuses. Storing the trimmed plain-text view makes a broken pair structurally impossible.
  • A window, not the whole history. Reads take the last 16 rows. Old rows stay — it's a log — but they stop being sent to the model, which bounds both cost and confusion.

What I'd question about this schema

You said you aren't convinced this schema is ideal. You're right not to be. Below is what I'd actually raise in review, worst first. Only the first one is a live defect; the rest are trade-offs that are currently fine and will stop being fine at a predictable moment.

Read this as a ranking, not a to-do list. Three of these cost nothing to fix and one of them is a real bug. The others you should decide about after using the app more — which is exactly what you said you wanted to do.

1. sent_reminders can ping you twice for the same thing

The comment on the table says each (task, kind) is recorded once. Nothing enforces that. The dedup is done in application code — read all the sent rows into a Set, check membership, then insert:

// queries.ts — the check
const sent = new Set(sentRows.map((r) => `${r.taskId}:${r.kind}`));

// queries.ts — the write, 6 lines later
export async function markReminderSent(taskId: number, kind: string) {
  await db.insert(sentReminders).values({ taskId, kind });   // no guard
}

Between the read and the write there is a gap. If two hourly ticks ever overlap — a retry, a slow run, a manual trigger while the cron fires — both read "not sent yet" and both insert. You get the same "due soon" ping twice, and the database was never asked to object.

The striking part is that the same file already contains the correct pattern, three functions down:

export async function markDigestSent(day: string) {
  await db.insert(sentDigests).values({ day }).onConflictDoNothing();
}

onConflictDoNothing() works there only because sent_digests.day is a primary key — there is a real constraint for the insert to conflict with. Take the key away and that line silently becomes a plain insert. The fix for reminders is the same shape: a UNIQUE (task_id, kind) constraint, then onConflictDoNothing(). One migration, one changed line, and the race stops existing rather than becoming unlikely.

The general lesson. "Check, then write" is not the same promise as "the database will refuse a duplicate." The first is a hope with a gap in the middle; the second is a fact. Whenever you find yourself writing the check in TypeScript, ask whether a constraint could hold it instead.

2. goals is two different tables wearing one coat

A goal has a kind — 'gate' or 'track' — and the columns that matter depend on which one it is:

ColumnApplies toMeaningless for
target_dategate — a date someone else settrack
weekly_targettrack — e.g. five applications a weekgate
milestonetrack — what counts as progressgate

All three are nullable, because each is null for one of the two kinds. That is the tell. Nothing prevents a gate with no target_date — which is a gate with no gate — or a track carrying a stray target_date from an earlier edit. Every piece of code that reads a goal has to re-derive which fields it's allowed to trust.

This pattern has a name: a nullable column that is only nullable because of a discriminator. Three ways out, cheapest first:

  • A CHECK constraint. One migration. CHECK (kind = 'gate' AND target_date IS NOT NULL AND milestone IS NULL OR kind = 'track' AND ...). The columns stay where they are; the illegal combinations become impossible. Ugly to read, effective.
  • Two tables, gates and tracks, each with only its own columns. Cleanest model, most churn — every query and the whole goals UI changes.
  • Leave it. Legitimate for a single-user app where you are the only writer and you know the rule.

My read: the CHECK constraint. It buys most of the correctness of splitting the table for a fraction of the work, and it documents the rule in the one place that can't drift from the code.

3. There is not one CHECK constraint in the entire schema

I grepped every migration. Zero CHECK, zero UNIQUE beyond the primary keys, zero CREATE INDEX. Several columns have a vocabulary of three or four legal values and a type that accepts any string at all:

ColumnLegal valuesWhat the DB accepts
tasks.focuslow · medium · highany text
goals.colorthe 7 category colour keysany text
goals.kindgate · trackany text
sent_reminders.kinddue_soon · overdueany text
assistant_turns.roleuser · assistantany text

Today TypeScript is the only thing standing between those columns and garbage. That holds right up until something writes to the database that isn't your app — a migration script, a manual psql fix at 11pm, an LLM-generated tool call. The assistant is now a writer, which moves this from theoretical to worth doing.

The reason it was skipped doesn't hold. Your CLAUDE.md says standard SQL only, no Postgres-only features, keep the database swappable. That rule correctly rules out a Postgres ENUM type. It does not rule out CHECK — CHECK is plain ANSI SQL and works on SQLite, MySQL, and every other target you'd ever swap to. Portability is a real constraint here; it just isn't a reason for this gap.

4. No indexes — and one table that grows forever

Right now this is correct. A few hundred rows fit in a page or two and Postgres will scan them faster than it could consult an index. Indexes are not free: each one slows every write and has to be kept in memory. Adding them "to be safe" is a real cost paid for an imaginary benefit.

But two queries will age badly, and it's worth knowing which:

  • loadDueSoonState() does SELECT * FROM sent_reminders with no WHERE clause, on every hourly tick, forever. The table only grows. A year of reminders is still small; five years of a busier you is not. The fix is a WHERE on recency, not an index.
  • assistant_turns is read as "the last 16 rows by at descending" and never pruned. Every Discord message you ever send lands here permanently. At a few thousand rows an index on at starts earning its keep.

Neither needs doing now. Both are worth a note so that when the app feels slow you look here first instead of guessing.

5. Two column choices that are inconsistent with themselves

jsonb pinned_fields

It holds a list of field names — ["urgency"]. That's a set of strings, which is exactly what categories is, and categories is a text[].

  • Two columns, same shape of data, two different types.
  • jsonb is a Postgres-only feature, which your own stack rule defers to phase 3.
  • Practically harmless. Worth knowing you have it, since it's the one place the swappable-DB rule is already broken.

float8 position

Manual drag order as a fractional index: to put a task between 1.0 and 2.0 you write 1.5, then 1.25, then 1.125.

  • Standard technique, genuinely good — reordering touches one row, not the whole list.
  • Known failure: repeatedly dropping a task into the same slot halves the gap each time. After roughly 50 you run out of double precision and the order silently stops being stable.
  • The standard answer is to renumber the list when the gap gets too small. Not worth building until you've felt it.

6. A goal can never be finished

tasks has done_at. goals has nothing equivalent — no done_at, no archived_at. A goal exists until you delete it, and deleting it sets goal_id to null on every task underneath, which is the same outcome as abandoning it. There is no way to record that you achieved something.

For an app whose whole point is getting you somewhere, that's a conspicuous hole. It's also the one item on this page I'd hold until you've used it more — the right shape depends on whether a finished goal should disappear from the UI, go grey, or move to a "done" section, and you can't answer that from the schema.
