1 · The contract

Foundry publishes one file. priority-post reads only that file. Neither knows the other's internals.

Written to inbox/inbox.json on main in thomas-tahk/foundry by a new scripts/inbox_publish.py, run at the end of each existing loop.

{
  "generated_at": "2026-09-07T18:00:00Z",
  "projects": ["thomas-tahk/pocket-draft", "thomas-tahk/priority-post", "thomas-tahk/knowflow"],
  "items": [
    {
      "id": "priority-post#42",
      "repo": "thomas-tahk/priority-post",
      "number": 42,
      "summary": "Add a settings screen for digest time",
      "detail": "Written from your note that the digest hour is buried in an env var.",
      "state": "waiting_on_you",
      "url": "https://github.com/thomas-tahk/priority-post/issues/42",
      "since": "2026-09-05T14:02:00Z",
      "actions": [
        { "key": "approve", "label": "Build it", "kind": "apply_label", "number": 42, "value": "factory:approved" },
        { "key": "decline", "label": "Not now",  "kind": "apply_label", "number": 42, "value": "factory:declined", "confirm": true }
      ]
    }
  ]
}
The rule that makes this work: priority-post never hardcodes a factory:* string. It applies whatever value the contract hands it. Foundry can rename every label tomorrow and priority-post keeps working.

state is a small closed vocabulary priority-post does know, because it drives colour: waiting_on_you · draft_ready · build_failing · branch_stranded.

kind is likewise closed: apply_label (a write priority-post makes) and open_url (just a link). There is no merge kind, ever. Merging stays on GitHub, under your finger.

Found during the build: every apply_label action carries its own number, because factory:try-again goes on the pull request, not on the issue that spawned it. An action inheriting the item's number would label the wrong thing.

projects is the elected list, carried in the same file so the plain-English intake can offer those projects and no others. Electing a project stays the one switch.

Validation

priority-post validates on read and renders nothing rather than something wrong: unknown state drops the item; unknown kind drops that action and keeps the item; a malformed file shows “Foundry's inbox couldn't be read” with a link to the raw file.

2 · How items appear

Design chosen: option E — mockups/foundry-in-the-list.html.

  • One line per item, sitting among real tasks, not in a block of their own.
  • No checkbox. Items appear when foundry says they need you and vanish when it doesn't. Nothing about them is “completed” from this side.
  • 3px left edge carries state colour — amber for everything, red for a failing build.
  • Primary action inline. Tapping opens the item in place for the detail and remaining actions. One open at a time.
  • Long summaries wrap, never truncate, under 480px.

Placement in the order — my call, flag it if wrong

Factory items have no urgency or importance, so the scorer can't rank them, and they aren't rows in tasks, so they can't be dragged.

Rule: they sit directly beneath the top task. Your single most important thing keeps the top slot; the factory sits where you can't scroll past it. Within the band: failing builds first, then waiting-on-you, drafts ready, stranded branches — oldest first inside each.

Not persisted

Fetched server-side per render with a 60-second cache, never written to Postgres. A stored copy eventually disagrees with GitHub, and a list that lies gets abandoned. Stage 1's display needs no migration.

3 · The hourly tick

No always-on host. No new accounts. $0/mo. All the brains already live in the app as /api/internal/*; the tick only supplies a timer and a way to post.

  • .github/workflows/tick.yml in priority-post (public repo = free unlimited Actions), cron: '0 * * * *', posting to /api/internal/tick with the secret header.
  • The workflow is fixed and never edited. What the tick does is runtime state.
  • At-least-daily is guaranteed by asking “is it past the digest hour and has today's digest not gone out?” — not “is it 20:00?”. A skipped tick fires an hour late instead of never. a new sent_digests table (migration 0004) is the record — sent_reminders is task-scoped with a foreign key, and a digest belongs to no task.
  • Due-soon pings stay inside the active window; outside it, events are dropped, not queued.
  • The digest posts via Discord webhook — no bot, no token, no intents, no gateway.
  • GitHub disables scheduled workflows after 60 days without a commit to the repo.

Timezone — the landmine. Railway let TZ be ambient. GitHub Actions runners and Vercel functions are both UTC, and Vercel's can't be set. So the zone has to stop being ambient and become an explicit contract.

  • New APP_TIMEZONE (America/Denver), read only through the existing config module.
  • Digest hour, active window, and “friday 3pm” all resolve from that value.
  • The agent's system prompt must state the timezone explicitly instead of embedding now.toString() and inheriting the process zone. That exact bug scored the eval 27/40 once — all 13 failures a one-hour offset. The model was correct given what it was told.
  • A test asserts the resolved offset, so a silent zone change fails the build rather than the digest.

4 · Plain-English intake

Independent of everything above — it shares no data shape with the inbox, which is why it can be built alongside stage 1 rather than after it.

One box in priority-post: “make the golf app deploy”.

  • Haiku turns the sentence into { repo, title, body }, choosing the repo from the elected list only.
  • You see it and confirm before anything is created. The model never files unattended.
  • On confirm, priority-post creates an ordinary GitHub issue via the API.
  • Foundry's builder already accepts a hand-written issue with no citation — nothing new is needed on the foundry side. That's what makes this cheap.

The issue then appears in the inbox on the next publish, closing the loop.
